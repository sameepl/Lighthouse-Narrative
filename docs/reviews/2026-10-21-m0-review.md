# M0 review, 2026-10-21

Review of the work merged or open at the time: PRs #14 (cycle contracts), #15 (encounter and keystone data), #16 (keystone scheduler), #17 (board selector) merged; #18 (simulation) and #19 (Hub flow, bridge) open.
Reviewer: Claude (tier A). Follow-ups are issues #20 to #29 (milestone "M0 hardening").

## What was checked

- `npm run check` on `main` (111 tests), PR #18 (115) and PR #19 (125): all pass.
- Code read: `src/engine/{cycle,board,rng,keystones,rules}.ts`, `src/data/{schema,validate,index}.ts`, the bridge in #19 (`run.ts`, `save.ts`, `roll.ts`, `session.ts`, `types.ts`), the ink changes, and the simulation in #18.

## Verdict

No blocking problems in #18 or #19; both can merge. The engine is pure, validated and well tested, randomness is injected and seeded, saves are validated before use, and the PR descriptions are honest about scope. The gaps below are about game design wiring, not about code quality.

## Findings

| # | Finding | Severity | Issue |
|---|---|---|---|
| 1 | **Crew trust can never rise.** It lives only in static `crew.json`; nothing raises or saves it. So "earn +1 Edge at trust 3" and the trust-3 assist bonus are unreachable. The simulation mutates trust itself, which hides the gap. | High (a core design loop is dead) | #20 |
| 2 | **Every action demands a ship**, even a conversation in the hall. `confirm()` throws "Assign a suitable ship" when none is chosen. | Medium | #21 |
| 3 | **Compact officials and protected people are assignable.** Prepare lists Renata, Halvorsen and Wren (Compact), Cass ("not crew") and Miri (canon: never operational, out of danger scenes). | Medium (canon) | #22 |
| 4 | **Offers are named from the id** ("written clause"); encounters have no display `title`. | Low | #23 |
| 5 | **Piece names drifted.** Code says `where / who / why`; the design says Removed, The Six, The Claim. No keystone data exists yet, so renaming is cheap now. | Medium (cheap now, expensive later) | #24 |
| 6 | **Keystone roles have no owner.** `KeystoneRoles` must be passed in code, and the app passes none. | Medium | #25 |
| 7 | **The simulation tests a copy of the loop**, not `RunController` or `GameSession`, so the two can drift apart. | Medium | #26 |
| 8 | **No dead-end guard in content tests.** If the first or final keystone ever has unmeetable `requires`, a run can stall. | Medium | #27 |
| 9 | **Hub prose lives in the bridge** ("...in this prototype", "1 actions left"). Prose belongs in the UI; the bridge should emit structured status. | Low | #28 |
| 10 | **Unpaid upkeep has no consequence**, and ships have no "in service" state. Design decision. | Decision | #29 |

### Smaller notes

- `RunController.end()` passes `{}` as the loud/quiet choice, so those Pursuit modifiers are never used. This is fine if the story uses `add("Pursuit", n)`; #28 documents that.
- After the first action of a cycle, the frozen board is re-run through `buildBoard`, so `unmetGuarantees` can report a guarantee as unmet simply because the crisis was already played. Harmless today; worth knowing when the Board screen shows warnings.
- #19 changed about 970 lines against the 300-line guideline. Justified for a tier-A change, but cards for core work should be split smaller next time (for example: Hub flow, Pursuit routing, saves).
- `upkeep` is charged for every ship every cycle (all ships are passed as "in service"); see #29.
- Ariadne is assignable like other crew; the design says she is never "busy". Decide later (noted on #22).
